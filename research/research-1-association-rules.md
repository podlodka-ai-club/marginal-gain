# Правило порождения связей и способ его проверки

Ресёрч к задаче `85da281b` для `podlodka-ai-club/marginal-gain`, ветка `memory-encoder`, коммит `9c2d7fb`.

---

## 0. Откуда числа

Карточек `Association` в хранилище ноль, поэтому измерить существующие связи нельзя. Мерить можно
только то, **сколько связей породило бы правило** и **предсказывает ли оно будущее**. Это и сделано.

Данные: локальный архив разговоров `~/.claude/projects`, 296 файлов, **1530 эпизодов**,
диапазон 2026-06-19 … 2026-08-25. Разбор — штатным парсером репозитория
(`understand.py: episodes_from_file / facts_of / fact_key`), без правок. Совпадение подтверждается:
парсер даёт ровно **787 файловых фактов**, то же число, что названо в задаче как испорченное.
То есть архив тот же, о котором идёт речь.

Что получилось на входе:

| Величина | Значение |
|---|---|
| эпизодов | 1530 |
| фактов извлечено | 1059 |
| различных фактов по `fact_key` (мера ADR 0002) | 623 |
| различных `subject` | **58** |
| различных `(fact_type, subject, scope)` | **78** |
| проектов | 82 |
| эпизодов **без единого факта** | 1095 (71.6%) |
| эпизодов с ≥2 различными фактами | 171 (11.2%) |

Скрипты одноразовые, лежат в `scratchpad/lab/` (`parse.py`, `cues.py`, `mrr.py`, `mrr2.py`,
`mrr3.py`, `cap.py`, `filt.py`, `defect.py`). В репозиторий ничего не добавлено, ничего не
закоммичено. SQL не использовался нигде: считалось по транскриптам, хранилище не трогалось.

## 1. Сначала — блокирующий факт про дефект `subject`

Дефект описан в задаче как «схлопывание в один ключ». Он не «портит качество» — он **обнуляет
задачу целиком**, и это надо предъявить числом до всякого разбора поводов.

Ключ карточки `Association` — тройка `source_key`-`target_key`-`cue`. Ключи концов это ключи
фактов в XMD. Пока ключ факта строится по `subject`, а `subject` это имя проекта:

| | узлов | рёбер `same_episode` на всём архиве |
|---|---|---|
| как есть сейчас (`subject` = проект) | **78** | **40** |
| если `subject` станет различающим (путь файла / адрес / тема) | 623 | 2086 |

1059 фактов сворачиваются в 78 узлов. Один узел `job-hunt` съедает 405 фактов, из них 378
файловых. Эпизодов, в которых нашлось хотя бы два **различных** узла, остаётся 54 из 1530.

Отсюда два следствия, оба жёсткие:

* **`same_file` в текущем виде невозможен физически.** Путь файла не входит в ключ узла вообще,
  различать нечего. Все 378 файловых фактов `job-hunt` — один и тот же узел, связь узла с самим
  собой не карточка.
* **`same_project` вырождается в петлю.** Все факты проекта уже один узел, «связать факты одного
  проекта» нечего.

Вывод, который надо записать первым пунктом решения: **до починки `subject` граф заполнять нельзя
ничем**. Не «получится хуже» — получится 40 карточек, из которых большинство про пересечение
проекта с темой предпочтения. Любая проверка на таком объёме не отличит правило от монетки.

Всё дальнейшее считано на **исправленной** идентичности факта (`fact_key`: путь файла для
файловых, адрес для внешних ресурсов, тема для предпочтений). Это ровно то, чем уже меряет
`holdout.py`, то есть проект внутри себя уже пользуется правильным ключом — не пользуется им
только запись в XMD.

## 2. Разбор пяти поводов

Правила, по которым считалось (одна строка на повод, чтобы можно было воспроизвести):

* `same_episode` — все пары различных фактов, извлечённых из одного эпизода;
* `same_file` — пары фактов, ссылающихся на один и тот же путь;
* `same_project` — пары фактов с одинаковым проектом (кроме `preference`, у них scope `global`);
* `adjacent_in_time` — пары фактов из соседних эпизодов одной сессии;
* `error_then_fix` — факт-препятствие из эпизода с `is_error` → файловые факты ближайшего
  последующего эпизода того же проекта с `outcome: done` в пределах суток.

### Сколько чего порождается

| Повод | Различных карточек | Доля графа | Макс. вес | Где шумит |
|---|---:|---:|---:|---|
| `same_episode` | 2086 | 6.8% | 7 | длинные эпизоды: 12 самых длинных дают 43% всех пар |
| `same_file` | **71** | 0.2% | 1 | почти не срабатывает: только 60 путей из 423 встретились в >1 проекте |
| `same_project` | **27259** | **88.5%** | 1 | клика на проект; один `job-hunt` (209 узлов) = 21736 карточек = 79% всего графа |
| `adjacent_in_time` | 1349 | 4.4% | 4 | переключение темы внутри сессии связывает несвязанное |
| `error_then_fix` | **29** | 0.1% | 4 | 45 эпизодов-источников, починка нашлась у 21 |
| **итого** | **30794** | | | |

Пересечения: `same_project` поглощает **95%** рёбер `same_episode` (1986 из 2086) и 100% рёбер
`error_then_fix`. То есть `same_project` не добавляет к остальным поводам почти ничего нового —
он их накрывает и топит.

### Что несёт каждый повод

**`same_episode`.** Сигнал: «эти утверждения понадобились для решения одной просьбы». Это ровно
то, ради чего связь и нужна на чтении — достали факт A, надо ли тянуть B. Единственный повод, у
которого источник сигнала совпадает с назначением связи.
Шум: длинный эпизод. Эпизод на 16 фактов даёт 120 пар, 12 самых длинных эпизодов (0.8% архива)
дают 43% всех пар. В таком эпизоде человек успел сменить тему, а связь получат все со всеми.
Лечится потолком (см. §4).

**`same_file`.** Сигнал должен быть сильным: одинаковый файл это буквально одно место в коде.
Цена: на нашем архиве **нечего связывать**. Ключ файлового факта уже содержит путь, поэтому два
факта об одном файле одного проекта — это один и тот же узел. Остаются только пары «один путь,
разные проекты» — 60 путей, 71 карточка, и это в основном одинаковые имена (`CLAUDE.md`,
`README.md`) в разных репозиториях, то есть ложные срабатывания по имени, а не по смыслу.
Повод не плох — **плох экстрактор**: он не выделяет из эпизода несколько разнотипных фактов про
один файл (правка, препятствие, адрес), поэтому связывать внутри файла нечего.

**`same_project`.** Сигнал: «относится к одному репозиторию». Слабейший из пяти и самый дорогой:
88.5% графа при полном отсутствии различающей силы — внутри проекта все пары равны. Рост
квадратичный: `job-hunt` за 68 дней дал 209 узлов и 21.7 тыс. карточек; втрое больше данных —
около 196 тыс. карточек на один проект.
Проверка ниже показывает: как ранжирующий признак он **хуже случайного** (MRR 0.0096 против
0.017–0.026 у случайного). При этом как **фильтр** он хорош: покрывает 60 из 70 будущих пар.
Отсюда решение в §3 — не карточка, а фильтр.

**`adjacent_in_time`.** Сигнал: «шло подряд». Заявка на причинность без причинности.
На архиве 1349 карточек. Проверка: покрывает 5 будущих пар из 70, MRR 0.0042–0.014, то есть
**на уровне случайного или ниже**. Внутри сессии соседство почти всегда либо совпадает с
`same_episode` (тогда повод лишний), либо означает смену темы (тогда повод вреден).
С `same_episode` пересекаются 320 рёбер из 1349 — то есть **76% этих связей это ровно то, что
`same_episode` связанным не считает**, и на замере они не подтверждаются.

**`error_then_fix`.** Единственный повод с направлением и с содержательным смыслом: «во что
упирались» → «чем починили». Это ровно то знание, ради которого память строят.
Цена: 29 карточек на весь архив, 0.1% графа. И — важнее — **проверить его нечем**: он покрывает
0 из 70 будущих пар, потому что препятствия почти не повторяются, а отложенные рёбра меряют
только повторяющееся. Это не «повод плохой», это «выбранная проверка его не видит» (§5).

## 3. Решение по правилу

**Нулевым шагом — починить `subject`.** Без этого пункты ниже не имеют предмета: узлов 78,
рёбер 40.

| Повод | Решение | Причина |
|---|---|---|
| `same_episode` | **берём, первая версия — только он** | единственный, у кого источник сигнала совпадает с назначением связи; единственный, кто прошёл проверку (MRR 0.107 при 0.017 у случайного, Hits@10 34.3% при 2–4%) |
| `error_then_fix` | **берём, но объёма нет и проверки нет** | сигнал содержательный и направленный, но 29 карточек и 0 покрытия на отложенных рёбрах; ставим, помечаем как непроверенный, не пускаем в порог чтения до отдельной проверки сценариями |
| `same_file` | **откладываем до починки экстрактора** | повод здоровый, материала ноль: 71 карточка, из них большинство ложные по совпадению имени файла. Вернуться, когда `facts_of` начнёт давать несколько разнотипных фактов на один файл |
| `adjacent_in_time` | **откладываем** | 1349 карточек за MRR на уровне случайного. Не отвергаем совсем: с окном в минутах, а не «соседний эпизод», может ожить. Сейчас платить 4.4% графа не за что |
| `same_project` | **отвергаем как карточку, оставляем как фильтр на чтении** | 88.5% графа, квадратичный рост, MRR хуже случайного. Но покрытие 86% будущих пар. Принадлежность проекту уже лежит в `subject`/`scope` факта — фильтровать по ней можно без единой карточки. Замер: фильтр вдвое сокращает пул кандидатов (393 → 200) без единой потери, метрики не меняются |

Итог первой версии: **`same_episode` + `error_then_fix`**, около **2115 карточек** на нынешнем
архиве против 30794, если брать все пять. Экономия 93% при том, что проверку проходит только
`same_episode`.

**Потолок на эпизод.** Замер на отложенных рёбрах с ограничением «не больше N фактов с
наибольшей оценкой на эпизод»:

| Потолок | Рёбер | MRR | Hits@10 |
|---:|---:|---:|---:|
| 4 | 321 | 0.0989 | 22.1% |
| 6 | 579 | 0.1193 | 26.4% |
| **8** | **858** | **0.1618** | **38.6%** |
| 10 | 1118 | 0.1597 | 34.3% |
| без потолка | 1566 | 0.1543 | 32.9% |

Потолок 8 даёт лучшие числа при вдвое меньшем графе. Оговорка честная: разница между 8, 10 и
«без потолка» лежит внутри шума на 140 запросах. Берём 8 как стартовое значение, а не как
доказанный оптимум.

**Вес.** `weight` = число подтверждений повода (сколько раз пара встретилась вместе).
`observed_at` — время последнего подтверждения, `first_seen_at` — первого. При чтении вес
складывается с крошечной добавкой популярности цели (0.01 нормированной частоты) — это разбивает
ничьи внутри соседства и на замере поднимает MRR с 0.107 до 0.154.

## 4. Способ проверки

### Три варианта, развёрнутые

**(а) Детерминированные правила, проверяемые сами собой.** Породить связи правилом и убедиться,
что они соответствуют правилу. Стоит ноль, объясняется в одну строку. Цена смертельная: проверка
тавтологична. Любая обучаемая надстройка — GNN, ILP, распространение меток из
`deep-research-report 3` §4 — на таких данных выучивает само правило и рапортует околоидеальное
качество. Это ровно та ловушка, в которую проект уже попадал: ADR 0002 описывает, как золотой
набор, выведенный из архива, дал «10 из 10» и не значил ничего. Повторять нельзя.

**(б) Разметка LLM.** Спросить модель, связаны ли два факта. Даёт сигнал, независимый от правила,
и это единственное, что умеет оценить **новый** повод. Цена: 30794 пары в полном варианте, даже
2115 в урезанном — это тысячи вызовов на каждый пересчёт. Хуже цены — шум: согласие двух прогонов
модели на парах вида «правился файл X» / «правился файл Y в том же проекте» будет того же
порядка, что измеряемый эффект (у нас эффект `same_episode` над популярностью — 10.7
процентных пункта по Hits@10). Мерить эффект в 10 пунктов инструментом с сопоставимым разбросом
нельзя.

**(в) Отложенные рёбра, MRR и Hits@K.** Архив режется по времени. Граф строится **только** по
первой половине. Истина берётся из второй половины и **не порождается правилом**: истинная пара —
это два факта, реально встретившиеся вместе в будущем эпизоде. Разметка не нужна, метрика
стандартная (`deep-research-report 3` §6). Цена честная: меряет только те поводы, чьи концы
успевают повториться.

### Выбран (в)

Причины: это единственный вариант, дающий число без разметки; он **уже** методологически принят
в проекте — `holdout.py` устроен так же (учимся на первой половине, проверяем на второй), значит
не вводится новой сущности; и он не тавтологичен, потому что истина берётся из сырого архива, а
не из правила. Вариант (б) остаётся в резерве ровно для того, чего (в) не умеет — см. §5.

### Процедура

1. **Граница.** По времени, `2026-08-11` (медиана по эпизодам). Устойчивость проверена на пяти
   границах: 08-05, 08-09, 08-11, 08-15, 08-19.
2. **Что прячем.** Всю вторую половину целиком. Граф строится только по эпизодам до границы.
3. **Истина.** Пары различных фактов, встретившиеся в одном эпизоде **после** границы, у которых
   **оба** конца уже существовали до границы. Это не «спрятанные рёбра правила» — это
   зафиксированное будущее совместное употребление, то есть буквально тот вопрос, на который
   связь отвечает при чтении: «достали A, тянуть ли B».
4. **Что меряем.** Для каждой истинной пары два запроса (A→B и B→A). Кандидаты — все узлы,
   известные до границы (393). Ранжируем по весу ребра из графа первой половины. Ничьи —
   средний ранг внутри группы равных. Считаем MRR, Hits@1, Hits@5, Hits@10.
5. **Базисы — два, и второй обязателен.** Случайный ранг и **ранжирование по популярности**
   (частота факта в первой половине, то есть мера из ADR 0002). Второй критичен: без него правило
   «побеждает» просто потому, что часто встречающиеся факты часто встречаются и дальше.

### Что получилось

Граница 2026-08-11: узлов до границы 393, истинных пар 70, запросов 140.

| Правило | MRR | Hits@1 | Hits@5 | Hits@10 | Рёбер | Покрытие истины |
|---|---:|---:|---:|---:|---:|---:|
| `same_episode` | **0.1072** | 5.0% | 13.6% | **34.3%** | 1566 | 33/70 |
| `adjacent_in_time` | 0.0094 | 0% | 0% | 0% | 1116 | 5/70 |
| `same_project` | 0.0096 | 0% | 0% | 0% | 20405 | 60/70 |
| `same_file` | 0.0051 | 0% | 0% | 0% | 38 | 0/70 |
| `error_then_fix` | 0.0051 | 0% | 0% | 0% | 19 | **0/70** |
| комбо (эп + сосед + ошибка) | 0.0988 | 2.9% | 13.6% | 32.9% | 2410 | 35/70 |
| базис: популярность | 0.0926 | 1.4% | 19.3% | 23.6% | — | — |
| базис: случайный ранг | 0.0234 | 0.7% | 2.1% | 4.3% | — | — |
| **мутация**: перепроводка `same_episode` | **0.0318** | 1.4% | 4.3% | 6.4% | 1478 | 6/70 |

### Число, которое считается успехом

Бутстрап на 5000 пересборок, 140 запросов:

* `same_episode` против случайного, разница MRR: 95% ДИ **[+0.060, +0.123]**, доля пересборок
  с неположительной разницей **0.000**.
* `same_episode` против популярности, разница MRR: 95% ДИ **[−0.020, +0.049]**, доля
  неположительных **0.198**. **Не значимо.**
* `same_episode` против популярности, разница Hits@10: 95% ДИ **[+0.007, +0.207]**, доля
  неположительных **0.020**. **Значимо.**

Отсюда критерий формулируется по Hits@10, а не по MRR, потому что MRR на нашем объёме данных
**не отличает правило от простого ранжирования по частоте**. Предъявлять MRR как доказательство
было бы тем же классом ошибки, что «10 из 10» в ADR 0002.

> **Успех: Hits@10 ≥ 0.30, и 95% доверительный интервал разницы Hits@10 с базисом популярности
> не содержит нуля.**
> Достигнуто: 0.343 при базисе 0.236, разница +10.7 п.п., ДИ [+0.7; +20.7] п.п.

### Мутация, доказывающая, что метрика вообще меряет

Порождаем связи случайным правилом с **сохранением распределения степеней** (перепроводка стабов:
то же число рёбер, те же веса, те же степени узлов, случайные концы). Сохранение степеней
обязательно — иначе мутация ломает заодно и популярность, и падение метрики ничего не докажет.

Требование: **MRR обязан упасть не менее чем втрое, до уровня случайного ранжирования
(≤ 0.04), а Hits@10 — до ≤ 10%.**
Получено: 0.1072 → 0.0318 (в 3.4 раза), Hits@10 34.3% → 6.4%. На пяти границах падение
в 3.0–7.1 раза. Метрика меряет структуру, а не объём графа.

Вторая мутация, тоже пройденная неявно: `same_project` порождает в 13 раз больше рёбер, чем
`same_episode`, и даёт MRR **ниже случайного**. Значит метрика не награждает за количество связей.

---

## 5. Явное ограничение выбранной проверки

Отложенные рёбра меряют повод **только если оба его конца успевают повториться после границы**.
Числа этого ограничения на нашем архиве:

* из 553 пар, встретившихся во второй половине, **обоими концами известны до границы только 70
  (13%)**. 87% будущей совместности — это факты, которых раньше не было. Проверка их не видит
  вовсе;
* `error_then_fix` покрывает **0 из 70** истинных пар. Препятствия не повторяются — в этом их
  природа. Повод, который мы решили брать, **этой проверкой не проверен и проверен быть не может**;
* `same_file` — тоже 0 из 70;
* новый повод, придуманный завтра, будет измерен только в той части, что пересекается с уже
  наблюдавшейся совместностью. Совсем новый вид связи так не проверить в принципе.

**Чем проверять новый повод.** Ответа, дающего число, у меня нет, и подставлять правдоподобный
я не буду. Что есть:

* **сценарии `evaluate.py`** — тот же путь, который ADR 0003 выбрал для протухания по той же
  причине («не через `holdout.py`, его мишень — частота»). Для `error_then_fix` сценарий
  формулируется: спросить про препятствие, ответ обязан содержать починку. Цена — сценарии
  выводятся вручную из архива, их десятки, а не тысячи, и они наследуют риск подгонки, о котором
  ADR 0002 уже предупреждал. Это не замена метрике, это другой, более слабый инструмент;
* **разметка LLM (вариант «б»)** — единственное, что даёт независимый сигнал на паре, которая
  никогда не повторится. Отвергнута по цене и шуму для массовой проверки, но для **одного** повода
  на выборке в сотню пар она посильна: 29 карточек `error_then_fix` можно разметить целиком.
  Это не проверено — предложение, а не результат;
* **прямой замер пользы** — поднимает ли связь долю успешных сценариев. Уперается в то, что README
  честно называет главной дырой: «умеем мерить, всплыло ли нужное, но не помогло ли оно». Пока
  меры пользы нет, замера пользы связи тоже нет.

Итог ограничения одной строкой: **первая версия правила состоит из двух поводов, и проверен из них
ровно один.** `error_then_fix` ставится на вере в его смысл, а не на числе, и это надо держать
записанным, а не забывать.

# ADR 0004. Правило порождения связей между фактами

Дата: 2026-08-25. Статус: черновик, не реализовано.

## Контекст

В схеме есть карточка `Association` с ключом источник-цель-повод и обязательным весом. Поводов
заявлено пять: `same_episode`, `same_file`, `same_project`, `adjacent_in_time`, `error_then_fix`.
Карточек в хранилище ноль. Ключ карточки в XMD не меняется — только пересоздание, поэтому
поставить связи и переставить потом дороже, чем выбрать правило заранее.

Мера из ADR 0002 отвечает на вопрос «стоит ли вообще воспроизводить этот факт». Связь отвечает на
другой: «достали факт A — тянуть ли за ним B». Это разные вопросы, и второй не решается порогом.

## Чего нельзя делать раньше всего остального

`subject` в разборе — имя проекта. Ключ факта строится по `subject`, поэтому 1059 фактов архива
сворачиваются в **78 узлов**, а один `job-hunt` съедает 405 фактов. На таком графе `same_episode`
даёт 40 рёбер вместо 2086, `same_file` невозможен физически (пути в ключе нет), `same_project`
вырождается в петлю.

Решение: **связи не ставить, пока `subject` не станет различающим** (путь файла для файловых
фактов, адрес для внешних ресурсов, тема для предпочтений). Ровно так уже устроен `fact_key`, по
которому считает `holdout.py`; правильный ключ у проекта есть, им не пользуется только запись
в XMD.

## Решение

Первая версия правила — **два повода из пяти**:

* **`same_episode`.** Пара различных фактов, извлечённых из одного эпизода. Потолок: не более
  8 фактов с наибольшей оценкой на эпизод, иначе длинный эпизод связывает всё со всем
  (12 самых длинных эпизодов архива дают 43% всех пар). Вес — число подтверждений.
* **`error_then_fix`.** Факт-препятствие из эпизода с отказом → файловые факты ближайшего
  последующего эпизода того же проекта с исходом `done` в пределах суток. Направленный,
  содержательный, редкий: 29 карточек на весь архив.

На нынешнем архиве это около **2115 карточек** против 30794, если брать все пять поводов.

При чтении вес ребра складывается с добавкой `0.01 * нормированная частота цели` — это разбивает
ничьи внутри соседства и поднимает MRR с 0.107 до 0.154.

## Отвергнутые альтернативы

| Что | Почему |
|---|---|
| **`same_project` как карточка** | 27259 карточек, 88.5% графа, рост квадратичный (`job-hunt`: 209 узлов → 21736 карточек, 79% всего графа). При этом различающей силы ноль: на отложенных рёбрах MRR 0.0096 — **ниже случайного** (0.0234). Повод поглощает 95% рёбер `same_episode` и топит их в клике. **Оставлен как фильтр на чтении**: принадлежность проекту лежит в `subject`/`scope`, фильтровать можно без единой карточки. Замер: пул кандидатов 393 → 200 без потерь |
| **`adjacent_in_time`** | 1349 карточек, MRR 0.0094 — на уровне случайного, покрывает 5 истинных пар из 70. Внутри сессии соседство либо дублирует `same_episode`, либо означает смену темы: 76% его рёбер (1029 из 1349) `same_episode` связанными не считает, и замер их не подтверждает. Отложен, не отвергнут: с окном в минутах вместо «соседний эпизод» может ожить |
| **`same_file`** | Повод здоровый, материала нет: 71 карточка, потому что факты об одном файле одного проекта — уже один узел, а межпроектные совпадения путей это `CLAUDE.md` и `README.md`, то есть ложные срабатывания по имени. Отложен до починки экстрактора: `facts_of` должен давать несколько разнотипных фактов на один файл (правка, препятствие, адрес), тогда внутри файла появится что связывать |
| **Проверка обучаемым методом (GNN, ILP, распространение меток)** | Связи порождены детерминированным правилом, обучаемый метод выучит само правило и отрапортует околоидеальное качество. Это тот же класс ошибки, что золотой набор из ADR 0002, давший «10 из 10» и не значивший ничего |
| **Разметка LLM как основная проверка** | Тысячи вызовов на пересчёт, и шум согласия модели на парах вида «правился файл X» / «правился файл Y» того же порядка, что измеряемый эффект (10.7 п.п.). Оставлена в резерве для точечной задачи — разметить целиком 29 пар `error_then_fix`, которых отложенные рёбра не видят |

## Как проверялось

Архив режется по времени. Граф строится **только** по первой половине. Истина берётся из второй
и правилом **не порождается**: истинная пара — два факта, реально встретившиеся вместе в будущем
эпизоде, при условии что оба конца уже существовали до границы. Для каждой пары два запроса,
кандидаты — все 393 известных узла, ничьи разрешаются средним рангом.

Базисов два, и второй обязателен: случайный ранг и **ранжирование по популярности** (частота из
ADR 0002). Без второго правило «побеждает» просто потому, что частое остаётся частым.

Граница 2026-08-11, 70 истинных пар, 140 запросов:

| Правило | MRR | Hits@5 | Hits@10 |
|---|---:|---:|---:|
| `same_episode` | **0.1072** | 13.6% | **34.3%** |
| базис: популярность | 0.0926 | 19.3% | 23.6% |
| базис: случайный ранг | 0.0234 | 2.1% | 4.3% |
| мутация: перепроводка с сохранением степеней | 0.0318 | 4.3% | 6.4% |

Устойчиво на пяти границах (08-05 … 08-19): MRR 0.107–0.129, Hits@10 33.3–40.3%.

**Критерий успеха: Hits@10 ≥ 0.30 и 95% ДИ разницы Hits@10 с базисом популярности не содержит
нуля.** Достигнуто: 0.343 против 0.236, разница +10.7 п.п., ДИ [+0.7; +20.7] п.п. (бутстрап,
5000 пересборок).

**Мутация:** случайное правило с сохранением распределения степеней обязано уронить MRR не менее
чем втрое, до уровня случайного (≤ 0.04), а Hits@10 до ≤ 10%. Получено 0.1072 → 0.0318
(в 3.4 раза), 34.3% → 6.4%. Сохранение степеней в мутации обязательно: иначе она ломает заодно и
популярность, и падение ничего не доказывает.

## Чего проверка не говорит

* **MRR у нас не значим.** Разница MRR с базисом популярности: ДИ [−0.020, +0.049], доля
  неположительных пересборок 0.198. Правило отличается от «ранжируй по частоте» только по
  Hits@10. Предъявлять MRR как доказательство нельзя.
* **87% будущего проверке недоступно.** Из 553 пар второй половины оба конца известны заранее
  только у 70 (13%). Остальное — факты, которых раньше не было.
* **`error_then_fix` не проверен и этой проверкой проверен быть не может**: покрытие 0 из 70,
  потому что препятствия по своей природе не повторяются. Повод берётся на вере в его смысл.
  Проверять его придётся сценариями `evaluate.py` — тем же путём, которым ADR 0003 проверяет
  протухание, и по той же причине: мишень отложенных рёбер это повторяемость.
* **Новый повод отложенными рёбрами не проверяется вовсе.** Способа, дающего число, сейчас нет.
* Выборка мала: 140 запросов. Разница между потолками 8, 10 и «без потолка» лежит внутри шума,
  поэтому 8 — стартовое значение, а не доказанный оптимум.

## Последствия

* Граф первой версии — около 2115 карточек, из них 2086 `same_episode`. Проверен один повод
  из двух.
* `same_project` живёт как фильтр на чтении, а не как карточка: 27 тысяч карточек, которых мы
  не создадим.
* Ключ карточки в XMD неизменяем, поэтому починка `subject` обязана пройти **до** первой записи
  связей. Иначе весь граф придётся пересоздавать.
* `error_then_fix` помечается как непроверенный и не участвует в пороге чтения, пока не появится
  его собственная проверка.

## Пересмотреть, если

* экстрактор научится давать несколько разнотипных фактов на один файл — тогда возвращаем
  `same_file`;
* появится мера пользы (README называет её главной дырой) — тогда связь можно мерить прямо по
  вкладу в успех сценария, и отложенные рёбра станут вспомогательными;
* архив вырастет так, что истинных пар станет не 70, а тысячи — тогда MRR начнёт отличать
  правило от популярности и станет годным критерием;
* `adjacent_in_time` с окном в минутах покажет покрытие выше нынешних 5 из 70.
